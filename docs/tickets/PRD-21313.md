## Product design

### Goals / Non-goals

Goals:
- Let an MCP-compatible agent, acting on behalf of one tenant's own Notion integration token, search the tenant's Notion workspace and read/write the two object types that cover almost all real Notion content: pages and databases (including the blocks that hold a page's body).
- Every call is logged (tool name, tenant, outcome) and uses only the credential supplied on that request — no credential or data is retained between calls (platform-wide MCP contract, not new to this ticket).

Non-goals (first version):
- Notion comments API (discussion threads) — no comment-related capability is implied by the ticket's generic wording; adding it later is additive.
- Workspace/user administration (invites, permissions) — out of scope, high blast radius, not requested.
- Creating or altering a database's *schema* (its property/column definitions) — only reading schema and reading/writing the *rows* (pages) inside a database. Schema edits are rarer, higher-risk (can break existing automations), and not implied by the ticket.
- Permanent deletion. Notion's API only exposes "trash" (archive), which is reversible; the tool surface offers archive/restore, never a hard delete.
- OAuth / Notion's public integration flow — this first version targets the simpler "internal integration" model (a single static API token per tenant, supplied via a request Header), matching every other MSPbots vendor MCP and the generic `/api/vendor-register` endpoint, which does not support OAuth (`mcp-track.md`; `vendor-mcp-development SKILL.md` "new vendor first-time registration").

### Acceptance criteria AC1..ACn

- AC1: Given a request to any tool without the `X-Notion-Api-Key` header, When the server handles it, Then it returns HTTP 401 with a body listing the missing header (no tool-specific logic runs).
- AC2: Given a valid API key for a tenant's Notion integration, When `notion_search` is called with a text query, Then it returns matching pages and/or databases the integration has been shared with, each with id, object type, title (best-effort extraction), url, and last_edited_time; pagination uses `next_cursor`/`has_more` and a `limit` capped at 50 by default / 200 max.
- AC3: Given a page id the integration can access, When `notion_get_page` is called, Then it returns the page's id, parent reference, archived flag, url, and its properties (collapsed to plain values, not Notion's raw rich-text objects).
- AC4: Given a page id the integration cannot access or that does not exist, When `notion_get_page` is called, Then it returns the structured error envelope with `code: "not_found"` (Notion's API returns 404 for both "doesn't exist" and "integration not shared" — the tool does not try to distinguish them, since doing so is not possible from the API response).
- AC5: Given a parent page id or parent database id and a set of properties, When `notion_create_page` is called, Then a new page is created under that parent and the tool returns its id and url; invalid property values (wrong type for the target database's schema, e.g. a string where a date is expected) return `code: "invalid_argument"` with Notion's validation message passed through.
- AC6: Given a page id and either updated properties or an `archived` flag, When `notion_update_page` is called, Then the change is applied and the updated page is returned; setting `archived: true` moves it to Notion's trash (reversible by calling again with `archived: false` — the tool never issues Notion's separate hard-delete-on-fixed-time behavior, there isn't one to call).
- AC7: Given a database id, When `notion_get_database` is called, Then it returns the database's id, title, url, and its property schema (name, type, and type-specific config such as select options) so a caller can construct valid `notion_create_page`/`notion_query_database` payloads without guessing.
- AC8: Given a database id and an optional filter/sort/`limit`, When `notion_query_database` is called, Then it returns the matching pages (same shape as AC3, one per row) with pagination; omitting the filter returns all pages the integration can see, paginated.
- AC9: Given a page id or block id, When `notion_list_block_children` is called, Then it returns that block's direct children (paragraphs, headings, lists, etc.) collapsed to a compact JSON shape (type + plain text + id), with pagination; nested children are not recursively expanded in one call (caller pages through them with the child's id if needed — keeps responses small, see AC13).
- AC10: Given a page id or block id and a list of new block objects (paragraphs, headings, bulleted list items — the common text block types), When `notion_append_block_children` is called, Then the blocks are appended at the end of that container and the tool returns the created blocks' ids; an unsupported block type in the input returns `code: "invalid_argument"` naming the first unsupported type, and nothing is partially appended (Notion's append call is atomic per request).
- AC11: Given no further filter, When `notion_list_users` is called, Then it returns the workspace's users (id, name, person/bot type) the integration can see, paginated; this tool is read-only and exists only so a caller can resolve a "person" property's id to a name, not for workspace administration.
- AC12: Given Notion's API returns 429 (or 529 service-overload), When any tool is called, Then the server retries with backoff honoring the `Retry-After` header (capped, see Non-functional), and if retries are exhausted, returns `code: "rate_limited"` rather than surfacing a raw 429/529.
- AC13: Given a result set that would exceed the server's 20000-character response cap, When any list/query tool is called, Then the response is truncated to fit, `has_more` (or `truncated`) is set, and the caller's `next_cursor` lets it continue — never an unbounded response.
- AC14: Given two concurrent requests for two different tenants (two different `X-Notion-Api-Key` values) hitting the same running container, When both are in flight at once, Then neither request's data, credential, or Notion API response is visible to the other request (per-request `contextvars` isolation; this is the platform-wide MCP contract, verified here because it is the only cross-tenant-isolation-relevant behavior this ticket adds).

### Open questions

- [ASSUMED, not blocking] Notion's public REST API has a formal "Notion-Version" header that must pin to one dated version string; the exact latest stable value should be re-read from `https://developers.notion.com/reference/versioning` at implementation time rather than hard-coded from this design (that page did not resolve to one unambiguous version number during this design pass). Assumption: pin to whatever is the current stable dated version at dev time, documented as a constant in one place. Not blocking — a wrong-but-valid version string is a one-line fix, not a design error.
- [ASSUMED, not blocking] Notion's 2025-era "data sources" model (a database can contain more than one data source) is out of scope for v1: `notion_get_database` / `notion_query_database` target the common case of a database with exactly one data source, using the longstanding single-data-source request/response shape. A database with multiple data sources is a recent, uncommon configuration; if the dev leg's real-account testing (once a tenant key is available) hits one, document it as a known gap rather than redesigning before any tenant has asked for it.
- [NOT BLOCKING] Whether `notion_search` should also expose Notion's `filter.value: "page"|"database"` and sort-by-last-edited knobs, or just free-text query — default to exposing both (they're native Notion API parameters, no extra design cost), but this is a detail the dev leg can simplify if it doesn't fit the ≤20-tool/short-description budget.

## Tech design

### Conclusion

Build `notion-mcp` from scratch per vendor-mcp-development SOP main line A: Python 3.12 + `uv` + FastMCP, Streamable HTTP, stateless, one container. Nine tools cover search + pages + databases + blocks + users (read path for the last one only). All state lives in Notion; the server is a thin, stateless translation layer between MCP tool calls and Notion's REST API, with the credential carried per-request in a Header and never persisted.

### Where the current implementation lives

Nothing — `MSPbotsAIFramework/notion-mcp@main` (1ef5429) is a one-line README, no code. This is a first version, not a modification.

The nearest sibling implementations for shape/conventions are other MSPbotsAIFramework vendor MCPs built under the same SOP (e.g. the HaloPSA and Alloy Navigator connectors referenced in prior PRD-21708 / PRD-21267 designs) — not read directly for this ticket (they are not public from this read-only pass), but the SOP they all follow (`vendor-mcp-development/reference/vendor-mcp-development-sop.md`) is the authoritative shape and is what this design follows directly.

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| Thin REST passthrough per Notion endpoint | One MCP tool per Notion REST endpoint (14+ endpoints) | Simplest mapping, no judgment calls | Blows past the "tools are capabilities, not endpoint mirrors" rule (SOP A4); duplicate/near-duplicate tools (e.g. separate "update properties" vs "archive" tools) | Rejected |
| Capability-grouped tools (this design) | 9 tools grouped by object (page/database/block/user), each tool doing one coherent job an agent would actually reach for | Matches SOP A4 guidance directly; keeps tool count low and descriptions short | Slightly more server-side logic per tool (e.g. `notion_update_page` branches on properties vs. archived) | **Chosen** |
| Use Notion's official `@notionhq/client` SDK, wrap in Node/TS | Official SDK handles auth header shape, retries | Less boilerplate | Every other MSPbots connector in this organization uses Python + FastMCP per the SOP's recommended stack; introducing Node here is the only service that would, raising ops cost for no scope benefit (SDK's value is thin — it is a REST wrapper, HTTP client in Python does the same job) | Rejected — no architecture reuse win big enough to justify the one-off stack |

No existing repo code to reuse (first version of this repo). Reuse is at the SOP/skeleton level: FastMCP app factory, the credential-context middleware pattern, and the error-envelope helper are boilerplate shared conceptually across every MSPbots vendor MCP; this design does not invent a new error model or auth model.

### Decisions made by DEV01

No one was available to ask (unattended design tick); these are the choices made for this first version, and why — change any of them by commenting and moving the ticket back to `5b - ready for groom`:

- Scope limited to pages, databases (rows only, not schema edits), blocks (common text types), and read-only users — because the ticket gives no object-level specifics beyond "live access" and this is the set that covers nearly all real Notion content without the higher blast radius of schema edits, workspace administration, or permanent deletion. Alternative considered: also ship comments and schema-edit tools day one — rejected, no demand signal and comments/schema changes are additive later if asked for.
- Credential model is a single static per-tenant API key via `X-Notion-Api-Key` (the "internal integration" model), not OAuth — because the generic `/api/vendor-register` path this repo registers through does not support OAuth; every other MSPbots vendor MCP uses the same Header-credential model. Alternative: Notion's public OAuth integration flow — rejected, it needs gateway/`mcp-manager` support this repo cannot provide (route to Leo Yang per SOP rule 5 if ever requested).
- One shared `cursor`/`limit` pagination shape across every list/query tool, rather than a bespoke shape per tool — because it is one less thing to document per tool and all six paginated tools map onto the same Notion cursor model. Alternative: per-tool custom pagination params — rejected, no benefit, more surface to get wrong.
- The exact `Notion-Version` header value is left as a named constant to be set at implementation time rather than guessed in this design — because asserting a specific dated version string now risks citing one that is stale or wrong by the time code is written, and a wrong constant is a one-line fix, not a design flaw.
- Databases with more than one "data source" (Notion's newer multi-source model) are out of scope for v1 — because it is a recent, uncommon configuration and the standard single-data-source shape covers the overwhelmingly common case. Alternative: build multi-data-source support now — rejected as premature complexity with no tenant having asked for it yet.
- `notion_append_block_children` accepts only the common text block types (paragraph, heading_1-3, bulleted_list_item, numbered_list_item, to_do) in v1, not Notion's full block type set (tables, columns, embeds, synced blocks, etc.) — because those cover the vast majority of "write page content" use cases with the least mapping complexity. Alternative: support all block types day one — rejected as scope creep without a specific request driving it.

### Data & API contract

Transport: `POST /mcp` (Streamable HTTP, per SOP §1.1), `GET /health` → `{"status": "ok"}` with no upstream dependency.

Credential header (per-request, never persisted, never read from env):

| Header | Required | Meaning |
|---|---|---|
| `X-Notion-Api-Key` | yes | The tenant's own Notion internal-integration secret (`Bearer ntn_...` format once passed to Notion; the Header itself carries just the raw secret). Obtained from Notion → Settings → Connections → Develop or manage integrations → the tenant's integration → "Internal Integration Secret". The integration must additionally be *shared* with the specific pages/databases the tenant wants reachable — Notion does not grant workspace-wide access by default; this is explained in the README, not solved in code. |

Missing header → `401`, body: `{"error": "missing_header", "required": ["X-Notion-Api-Key"]}`.

Tool error envelope (uniform across all 9 tools, SOP §4):

```json
{"error": {"code": "not_found", "message": "Page not found or not shared with this integration", "retryable": false}}
```

`code` is one of: `not_configured` (used only if a future OAuth path is added — unused in this v1, which has nothing to "configure" beyond the Header), `unauthorized` (Notion 401 — bad/revoked key), `not_found` (Notion 404), `invalid_argument` (Notion 400 validation errors — message passed through), `rate_limited` (after retries exhausted on 429/529), `upstream_error` (any other non-2xx from Notion, or a network/timeout failure after retries).

Nine tools (`notion_<verb>_<resource>` naming, SOP A4):

| Tool | Verb semantics | Key params | Annotations |
|---|---|---|---|
| `notion_search` | search workspace | `query` (str), `filter_object_type` (`page`\|`database`, optional), `cursor`, `limit` | readOnlyHint |
| `notion_get_page` | retrieve one page | `page_id` | readOnlyHint |
| `notion_create_page` | create one page | `parent_page_id` or `parent_database_id` (exactly one), `properties` (flat key→value map, mapped to Notion's typed property JSON) | (write, not destructive, not idempotent) |
| `notion_update_page` | update properties and/or archive/restore | `page_id`, `properties` (optional), `archived` (optional bool) | idempotentHint (re-applying the same update is a no-op change) |
| `notion_get_database` | retrieve schema | `database_id` | readOnlyHint |
| `notion_query_database` | list rows | `database_id`, `filter` (optional, Notion filter object passed through), `sorts` (optional), `cursor`, `limit` | readOnlyHint |
| `notion_list_block_children` | read page/block content | `block_id` (a page id is also a valid block id in Notion's model), `cursor`, `limit` | readOnlyHint |
| `notion_append_block_children` | write page/block content | `block_id`, `children` (list of simplified block objects: `type` + plain text, limited to paragraph/heading_1-3/bulleted_list_item/numbered_list_item/to_do in v1) | (write, not destructive, not idempotent — appends grow the page) |
| `notion_list_users` | list workspace members | `cursor`, `limit` | readOnlyHint |

Request/response examples (abbreviated):

```
notion_search {"query": "Q3 roadmap", "limit": 20}
→ {"results": [{"id": "1a2b...", "object": "page", "title": "Q3 Roadmap", "url": "https://notion.so/...", "last_edited_time": "2026-10-20T10:00:00Z"}], "has_more": false, "next_cursor": null}

notion_create_page {"parent_database_id": "db123", "properties": {"Name": "New task", "Status": "Todo"}}
→ {"id": "pg456", "url": "https://notion.so/..."}

notion_update_page {"page_id": "pg456", "archived": true}
→ {"id": "pg456", "archived": true}
```

Backward compatibility: not applicable — no prior version of this tool surface exists. Future changes follow SOP §13 (breaking changes announced, additive changes free) once a first version is live.

No database/schema of our own — there is no persistence layer in this service (stateless passthrough to Notion).

### Key flow / sequence

```
Agent → Gateway (adds/forwards X-Notion-Api-Key) → notion-mcp /mcp
  tools/call "notion_search" {query}
    → middleware: extract header → 401 if missing → set contextvar
    → tools.py: validate params (pydantic) → notion_client.search(cred, query, cursor, limit)
       → httpx POST https://api.notion.com/v1/search (Authorization: Bearer <cred>, Notion-Version: <pinned>)
       → 200: shapes.py collapses results → tool returns JSON string
       → 429/529: retry with backoff honoring Retry-After, up to the request budget; exhausted → {"error": {"code": "rate_limited", ...}}
       → 4xx/5xx other: map to envelope, return (no exception propagates to the MCP transport)
    → middleware finally: reset contextvar
```

### Non-functional

- **Idempotency & concurrency**: every tool call is a single Notion REST call (or a bounded retry loop over the same call); there is no multi-step server-side transaction to make atomic. `notion_update_page` is safe to retry (Notion's PATCH is idempotent for the same payload). `notion_append_block_children` is NOT safe to blindly retry on a network timeout with an unknown server-side outcome (could double-append) — the server only retries on responses it received (429/529), never on a timeout where the response is unknown; a timed-out append surfaces `upstream_error` and the caller decides whether to retry, this is documented in the tool description.
- **Performance**: Notion's real limit is ~3 req/s for most workspace plans (confirmed 2026-11-02, `developers.notion.com/reference/request-limits`), up to ~10 req/s on Business/Enterprise. The server does not pool/batch across tenants (each request has its own credential and its own `httpx.AsyncClient`), so this ceiling is per-tenant and enforced by Notion itself, not by this service; the service's own job is to not make it worse (reuse one client per request, not open a new TCP connection per retry attempt, respect `Retry-After` exactly rather than a fixed backoff that might under- or over-wait).
- **Security**: credential only ever in the `X-Notion-Api-Key` header and the outbound `Authorization: Bearer` header built from it per request; never logged (logs record tool name, tenant marker if the gateway supplies one, and outcome code — never the header value or full Notion response bodies, which can contain page content); never written to disk or env.
- **Multi-tenant isolation**: `contextvars.ContextVar` set in middleware, read in `notion_client.py`, reset in `finally` — the standard MSPbots MCP isolation pattern (AC14); no module-level or class-level state holds a credential or a per-tenant cache.
- **Observability**: structured log line per tool call: tool name, outcome code (`ok` or the error `code`), latency, and whether a retry occurred — enough to see rate-limit pressure or a sick upstream without needing response bodies.

### Rollout & rollback

Single repo, no feature flag needed (first version, no existing traffic to break). Rollout is the SOP's standard path: merge to `main` → `/api/vendor-register` (first-ever registration for this vendor name `notion`, since the network is not registered in INT's gateway yet) → INT. `credential_fields` for registration: `{"X-Notion-Api-Key": {"label": "Notion Internal Integration Secret", "type": "password", "required": true, "description": "From Notion → Settings → Connections → Develop or manage integrations → your integration → Internal Integration Secret. The integration must also be shared with the pages/databases you want reachable.", "example": "ntn_xxx"}}`.

Rollback: before any tenant has connected, rollback is "do not route traffic to this vendor" — no data migration, nothing stateful to undo. After real tenants connect, a bad release is rolled back by redeploying the previous `main` commit through the same publish API (no DB to restore, since this service holds no data of its own).

### Risks & dependencies

- Risk: the exact `Notion-Version` to pin may have moved by the time of implementation (Notion ships dated versions periodically) — mitigation: read `developers.notion.com/reference/versioning` at dev time, pin one value, document it in `settings.py` as a named constant (one-line fix if wrong).
- Risk: a tenant's database uses the newer multi-data-source model, which this v1 does not specifically branch on — mitigation: documented Open Question; `notion_get_database`/`notion_query_database` calls will return whatever the pinned API version's standard database shape gives; if this becomes a real support ticket, it is an additive follow-up (new optional `data_source_id` parameter), not a redesign.
- Risk: no test Notion account exists today — not a blocker per SOP ("no test account" is explicitly non-blocking); flagged test cases exist for when one is available, and mocked-transport tests give coverage without one.
- Dependency: none on other open tickets or other repos. This repo stands alone; nothing in `mcp-service-gateway` needs to change (generic Header-credential vendor, matches the existing `/api/vendor-register` contract with no OAuth).
